## 1. Visión Estratégica del Proyecto

### 1.1 Declaración de Visión

> *"Transformar la gestión del gimnasio en una experiencia digital integral donde cada cliente tenga un seguimiento personalizado, cuantificable y visual de su progreso físico, generando mayor retención, satisfacción y resultados medibles en un período de 6 meses."*

### 1.2 Misión del Sistema

- **Centralizar** toda la información de 100 clientes en una plataforma única.
- **Automatizar** evaluaciones cada 21 días para reducir carga operativa del entrenador.
- **Visualizar** el progreso con gráficos que motiven al cliente y faciliten la toma de decisiones.
- **Cuantificar** resultados para demostrar el valor del servicio de entrenamiento personalizado.

### 1.3 Objetivos Estratégicos

| # | Objetivo | Horizonte |
|---|---|---|
| OE-1 | Reducir el tiempo de registro de métricas de un cliente en un 70% | Corto plazo (3 meses) |
| OE-2 | Aumentar la retención de clientes en un 25% mediante seguimiento visual | Mediano plazo (6 meses) |
| OE-3 | Generar evaluaciones automáticas sin intervención manual cada 21 días | Corto plazo (4 meses) |
| OE-4 | Mejorar la satisfacción del cliente mediblemente (encuestas > 8.5/10) | Mediano plazo (6 meses) |
| OE-5 | Escalar el modelo a más de 100 clientes sin degradación de performance | Largo plazo (12 meses) |

## 2. Análisis de Pareto (80/20)

> **Principio:** El 20% de las funcionalidades generarán el 80% del valor percibido por los usuarios (entrenadores y clientes).

### 2.1 Las 8 Funcionalidades del 80% del Valor

De las 37 funcionalidades identificadas en el plan de trabajo, el análisis Pareto determina que aproximadamente 7-8 funcionalidades generan el 80% del impacto.

| # | Funcionalidad | ID Requisito | % de Valor | Justificación |
|---|---|---|---|---|
| 1 | **CRUD de Clientes** | RF-001, RF-002 | 15% | Sin clientes no hay sistema. Base de todo. |
| 2 | **Registro de Métricas Físicas** | RF-006 a RF-011 | 15% | El corazón del sistema. Peso, grasa, BMI, Kcal basal. |
| 3 | **Galería de Fotos Corporales** | RF-004, RF-013 | 12% | Impacto visual máximo. El cliente "ve" su progreso. |
| 4 | **Evaluaciones Automáticas cada 21 días** | RF-020 a RF-023 | 12% | Diferenciador clave. Automatización = ahorro de tiempo. |
| 5 | **Gráficos de Progreso** | RF-029 a RF-032 | 10% | Cuantificación visual. Motivación del cliente. |
| 6 | **Registro de Asistencia** | RF-018 | 8% | Métrica de compromiso. Detecta abandono temprano. |
| 7 | **Rutinas y Registro de KG** | RF-014 a RF-017 | 5% | Seguimiento de entrenamiento. Progresión de cargas. |
| 8 | **Exportación a PDF** | RF-033 | 3% | Entregable profesional al cliente. Valor percibido alto. |
| | **TOTAL 20% Crítico** | | **80%** | |

### 2.2 Las 29 Funcionalidades del 20% Restante

| Categoría | Funcionalidades | % Valor |
|---|---|---|
| Medidas Corporales Detalladas | Cintura, cadera, pecho, brazos, muslos | 5% |
| Estado de Ánimo | Registro semanal | 3% |
| Alimentación | Tracker diario | 3% |
| Satisfacción | Encuestas | 3% |

| Notas del Entrenador | Campo libre | 1% |

| Otros (configuraciones, perfiles, etc.) | | 0% |

### 2.3 Estrategia Pareto Aplicada al Desarrollo

**FASE 1-2 (Semanas 1-5): DESARROLLAR PRIMERO las 8 funcionalidades críticas**
- CRUD Clientes + Métricas + Fotos + Evaluaciones + Gráficos
- Esto entrega el 80% del valor en solo 5 semanas

**FASE 3-5 (Semanas 6-13): DESARROLLAR DESPUÉS las funcionalidades complementarias**
- Rutinas, asistencia, medidas, ánimo, alimentación, satisfacción
- Refinan la experiencia pero no son bloqueantes

**FASE 6-7 (Semanas 14-16): PULIR, TESTEAR Y DESPLEGAR**
- Reportes, exportaciones, optimizaciones, documentación

### 2.4 Decisión Estratégica: MVP vs Producto Completo

| Enfoque | Funcionalidades | Tiempo | Valor Entregado |
|---|---|---|---|
| **MVP Pareto** (Recomendado) | 8 funcionalidades críticas | 5 semanas | 80% del valor |
| **Producto Completo** | 37 funcionalidades | 16 semanas | 100% del valor |

> **Recomendación estratégica:** Desplegar el MVP Pareto a las 5 semanas para que el gimnasio empiece a usarlo inmediatamente. Las funcionalidades restantes se agregan en releases posteriores.

### 5.3 Plan de Respuesta a Riesgos Críticos

#### R-1: Retraso por Alcance Creciente
```
Trigger: Solicitud de nueva funcionalidad durante el desarrollo
Respuesta:
  1. Evaluar si entra en el 20% Pareto crítico
  2. Si SÍ: Reemplazar funcionalidad de menor prioridad (intercambio)
  3. Si NO: Agregar a backlog para Release 2
  4. Documentar decisión y comunicar impacto en cronograma
```

#### R-2: Pérdida de Datos
```
Trigger: Fallo de servidor, error humano, ataque
Respuesta:
  1. Backup automático diario a las 02:00 AM (Laravel Backup)
  2. Backup semanal exportado a Dropbox/S3 externo
  3. Prueba de restauración el primer lunes de cada mes
  4. RPO (Recovery Point Objective): máximo 24 horas de datos perdidos
  5. RTO (Recovery Time Objective): sistema restaurado en menos de 4 horas
```

#### R-3: No Adopción por el Personal
```
Trigger: Entrenadores siguen usando Excel/papel después de 2 semanas
Respuesta:
  1. Identificar resistencia: ¿técnica? ¿cultural? ¿tiempo?
  2. Si técnica: Capacitación adicional 1-a-1
  3. Si cultural: Mostrar caso de éxito de un entrenador early-adopter
  4. Si tiempo: Simplificar flujo de trabajo (menos clicks)
  5. Último recurso: Designar "campeón digital" que ayude a otros
```

## 10. Plan de Contingencia

### 10.1 Escenarios de Contingencia

#### Escenario A: Retraso de 2+ Semanas en el Desarrollo
```
Trigger: Cualquier fase se retrasa más de 1 semana
Acciones:
  1. Revisar alcance de la fase actual con método Pareto
  2. Mover funcionalidades "Could have" (MoSCoW) a Release 2
  3. Congelar nuevos requisitos hasta recuperar el timeline
  4. Considerar agregar un desarrollador adicional (si presupuesto lo permite)
  5. Comunicar nuevo timeline al gimnasio con 1 semana de anticipación
```

#### Escenario B: Fallo Crítico en Producción
```
Trigger: Sistema caído > 30 min o pérdida de datos
Acciones:
  1. Activar modo mantenimiento: php artisan down
  2. Restaurar último backup válido (RPO: 24 horas máximo)
  3. Comunicar a entrenadores vía grupo de WhatsApp
  4. Investigar causa raíz con Laravel Telescope logs
  5. Implementar fix y desplegar
  6. Documentar post-mortem
  7. php artisan up
```

#### Escenario C: Personal del Gimnasio No Adopta el Sistema
```
Trigger: < 50% de entrenadores usan el sistema después de 3 semanas
Acciones:
  1. Entrevistar a entrenadores resistentes (1-a-1, 15 min)
  2. Identificar barrera: técnica, cultural o de tiempo
  3. Barrera técnica: Capacitación adicional + manual impreso
  4. Barrera cultural: Designar "early adopter" como embajador
  5. Barrera tiempo: Simplificar flujo (reducir clicks necesarios)
  6. Último recurso: Hacer uso del sistema obligatorio para reportes
```

#### Escenario D: Excedente de Presupuesto
```
Trigger: Gasto supera 80% del presupuesto antes de la mitad del proyecto
Acciones:
  1. Revisar Pareto: ¿Qué funcionalidades del 20% restante pueden postergarse?
  2. Negociar alcance con el gimnasio (Release 1 vs Release 2)
  3. Considerar alternativas de hosting más económicas (Shared → VPS → Cloud)
  4. Postergar funcionalidades "nice to have" indefinidamente
  5. Documentar deuda técnica para resolver en mantenimiento futuro
```

#### Escenario E: Desarrollador Principal No Disponible
```
Trigger: Dev Lead enfermo, renuncia o incapacitado > 1 semana
Acciones:
  1. Acceder al repositorio de código (debe estar en GitHub/GitLab)
  2. Revisar documentación técnica en /docs del proyecto
  3. Contactar desarrollador de respaldo (debe estar identificado previamente)
  4. Usar Laravel Sail para que cualquier dev con Docker pueda levantar el proyecto
  5. Priorizar solo fixes críticos hasta que el dev principal regrese
```
